# Codex改修指示書｜現場アドバイザー：Teams入力・Teams回答・SharePoint/Power Apps連携

**作成日:** 2026-11-04  
**優先度:** 高  
**対象:** 既存の Copilot Studio エージェント／トピック・ナレッジ・Power Automate（クラウドフロー）・SharePoint 連携・必要最小限の Power Apps 側調整  
**基本方針:** **既存システムを活かす差分改修。新規にシステムを作り直さない。既存機能を削らない。実行可能なものは実装し、環境接続が必要なものは具体的な適用手順まで作成する。**

---

## 0. Codexへの最重要指示

この依頼は**構想の相談ではなく、既存エージェントの実装・改修依頼**である。渡されたリポジトリ／エクスポート／設定ファイルを先に全て調査し、できる範囲を実装すること。

- **現場の入口はスマホ版 Microsoft Teams。回答もTeamsで完結**させる。現場ユーザーにPower Appsを開かせない。
- **事務所では既存のPower Appsを継続使用**する。Teams回答とは別に、既存アプリが読める文章をSharePointに保存する。
- Teamsからの投稿（**写真付きも含む**）で**同じ既存Copilot Studioエージェント**が動くこと。
- **「現場アドバイス」「マニュアル確認」「マニュアル改訂」等の既存分岐、画像判定、記録、再質問、ナレッジ検索等を壊さない。** 既存の正しい処理を置換・削除しない。
- **修理方法の質問は、根拠となるマニュアルを検索し、Teamsに正確・わかりやすく・速く返す。** その回答文章もSharePointに記録する。
- 修理方法を聞いた後でも、次に現場写真・状況の更新が送られたら**通常の現場アドバイス処理へ復帰**する。
- **TeamsでSharePointに登録されない現象を必ず原因切り分け・対策**する。表示文を変更するだけでは完了にしない。
- **優先度の変更点は同一案件の前回報告との比較**。同一チャットでも案件が違えば比較しない。
- 根拠不明なガス保安／修理の指示を生成しない。マニュアルや入力から確認できない事実は「未確認」と扱う。
- 現場写真・社内情報・権限を保護し、社外サービスへの無断転送や認証の無効化を行わない。

> **重要:** リポジトリにPower AutomateやSharePointリストの定義が存在しない場合、接続先の実際の値を想像して実装済みと報告してはいけない。ソースから確認できるところはコード・設定に反映し、クラウド環境上での操作が必要な部分は、画面項目名・手順・入力値の確認方法・検証方法を明示する。

## 1. 現状と既知の問題

### 1.1 既存運用

- Copilot Studioで現場アドバイザーを構築済み。
- 保安柵、ポケット警報器、ガス濃度など、初動措置に関するマニュアル参照・現場判断を行う。
- **Microsoft 365 Copilotから使うとSharePointへ情報が登録され、事務所のPower Appsに結果が反映される。**
- 既存Power Appsはすでに作成済み。SharePointの更新結果を取り込み、視覚的に見やすく表示する。
- 一方、**スマホ版Microsoft 365 Copilotでは写真添付ができない状態**。
- **スマホ版Teamsでは写真を添付できそうだが、回答品質が不安定で、SharePointが登録／更新されない。** そのためPower Appsにも表示されない。
- Power AutomateにはSharePointの **「項目が作成されたとき」** をトリガーにする既存フローがある。これは**項目作成後の処理**であり、SharePointへの最初の書込み元とは限らない。通知には一定の遅延が生じている。
- Copilot Studioの「ツール」一覧が空だったことがある。したがって、書込み処理がトピック・別フロー・Microsoft 365 Copilot側など、どこで実行されているかは**未特定**。

### 1.2 過去構成についての調査手掛かり（実ファイルと照合すること）

- SharePointサイト名候補：`TGNW_アプリ維持管理サイト`
- SharePointリスト名候補：`AI_エージェント可視化`
- 案件識別子候補：`CaseId`
- 以前のエージェントには、**「マニュアル確認」「マニュアル改訂」「現場アドバイス（画像認識含む）」の3系統の分岐**があった。
- マニュアルでは `MS-016`（保安柵）、`MS-009`（ポケット警報器）、`MS-015`（濃度）等が扱われていた。
- 以前の実装で、CaseIdの重複確認を行っていたことがある。

**上記は調査の手掛かりであって、現在の本番環境の確定スキーマではない。実ファイルと実環境を優先する。** 過去の名称や列名を根拠なく新設・置換しない。

## 2. 採用する運用・構成

```text
【現場担当者（スマホ）】
 Microsoft Teams：既存Copilot Studioエージェントへのチャット
   ├─ 現場状況（文章）
   ├─ 現場写真（1枚以上・対応範囲内）
   └─ 修理方法に関する質問
                │
                ▼
【既存 Copilot Studio エージェント】
   ├─ 入力の種別を判定
   │    ├─ 現場情報・更新 → 既存の現場アドバイス分岐
   │    ├─ 修理方法の質問 → 既存ナレッジ検索／マニュアル確認分岐
   │    └─ その他の既存分岐 → 従来どおり保持
   ├─ 画像理解（写真がある場合）
   ├─ マニュアルに基づく判断・根拠照合
   ├─ 案件ごとの直前の現場報告を参照（2回目以降）

           ▼                       ▼
【Teams向け可読回答】       【SharePointへ記録】
  現場ユーザーが読む           ├─ 現場アドバイス：既存Power Apps用の文章
  画面切替え不要               └─ 修理回答：Teamsと同じ回答文章
                                      │
                                      ▼
                            【既存 Power Apps】
                             事務所で一覧・判定を表示
```

**禁止:** 現場ユーザーに「Teamsで送信 → Power Appsを開いて回答確認」を強制する設計。

## 3. 機能要件A：現場アドバイスのTeams回答（最重要）

### 3.1 表示する項目と順序

Teamsに返す現場アドバイスは、**次の順番**を原則とする。

1. **前回の報告からの優先度の変更点**：**同一案件で2回目以降の報告のみ表示**。初回はこのセクション自体を表示しない。
2. **優先度別の初動措置項目**：**高・中・低**。各項目に具体的な状態と必要な対応を短く書く。
3. **確認したいこと**：判断を確定させるために不足している現場情報。重要度の高い順に質問する。
4. **ネクストアクションの要約**：現場担当者が次に何をするべきか、一読で分かる文章。

- Teamsでは**生のJSON、列名、機械用マーカー、Power Apps解析専用の文章**を表示しない。
- 冒頭に短い案件名／日時／状況ラベルを添えてもよい。ただし上記4項目の順序は変えない。
- スマホ向けに見出し・改行・強調を使い、長文を避ける。重要項目は埋もれさせない。
- **優先度「高」に該当する重要項目は「低」より先**。ゼロ件の場合は「該当なし」と表示し、情報不足と該当なしを混同しない。
- 高・中・低の判定根拠が既存マニュアルに依存するなら、その定義や優先順位を既存仕様から引き継ぐ。新しい独自安全基準を勝手に導入しない。
- 判断に使ったマニュアルの番号・節・該当箇所など、**特定できた根拠は簡潔に表示**する（存在しない出典は書かない）。

### 3.2 Teams表示例（画面レイアウトの例。保安上の判定内容を示すものではない）

**初回の投稿：**

```text
📍 現場アドバイス｜案件 A-001

【② 初動措置の優先度】
🔴 高
・項目A：追加確認が必要（理由：撮影範囲外で確認できない）

🟠 中
・項目B：要確認（根拠：該当マニュアルの確認項目）

🟢 低
・該当なし

【③ 確認したいこと】
1. 項目Aの状況が分かる写真を追加できますか？
2. 項目Bは実施済みですか？

【④ ネクストアクション】
・未確認の状況を追加報告してください。
・必要な措置はマニュアルおよび社内ルールで確認してください。
```

**同一案件の2回目以降：**

```text
📍 現場アドバイス｜案件 A-001（更新）

【① 前回報告からの変更点】
⬆ 項目B：中 → 高（新たな現場情報により優先度上昇）
➡ 項目A：高 → 高（変更なし。必要な場合のみ表示）
※不明な項目は「解消済み」とみなさない。

【② 初動措置の優先度】
🔴 高
・項目B：追加確認・対応が必要
・項目A：引き続き状況確認が必要

🟠 中
・該当なし

🟢 低
・該当なし

【③ 確認したいこと】
1. 項目Bの追加情報はありますか？

【④ ネクストアクション】
・優先度が上がった項目Bを確認してください。
・未確認の項目Aの状況を確認してください。
```

**注:** 見出しに付けた `①〜④` は要求の対応関係を示す例。**初回には①を出さないこと**。初回だけ②③④の表記を①②③へ詰め直してもよいが、実装全体で統一する。

### 3.3 前回比較の厳密なルール

- **同一CaseIdの直前の「現場アドバイス」記録**を比較元とする。直前の「修理回答」は比較対象にしない。
- **同じ案件か判断できないときは、別案件の情報を勝手に引き継がない。** 明示的な案件選択・既存CaseId・信頼できるセッション紐付けを利用する。確定できないときは必要な確認を求める。
- 優先度変更は**同じ初動措置項目の旧優先度と新優先度**を比較する。文章の言い回しの変化だけを「変更」としない。
- 「新規項目」「高→中などの優先度変化」「未確認→確認済みなどの状態変化」「対応完了」は区別して扱う。
- **写真に写っていない／報告に書かれていないことを、未実施・解消・安全確認済みと断定しない。** 未確認は未確認のまま保持する。
- 変更がなければ、2回目以降は「前回から優先度の変更なし」と短く表示してよい。
- 過去データがない初回は変更点欄を出さない。過去データ取得エラー時に「変更なし」と偽装しない（例：「前回比較は現在できません」）。
- 複数ユーザーや同時投稿でデータが混ざらないよう、案件単位の識別と更新順序を管理する。

### 3.4 画像付きTeams投稿

- 添付写真が**実際にエージェントまで渡り、内容を判断に使用できる**ことを検証する。「Teams画面に添付アイコンがある」だけでは合格としない。
- 文章だけ、画像だけ、文章＋画像、写真追加（2回目以降）を扱う。
- 可能なら既存の画像分析・事実抽出ロジックをそのまま使う。画像の解釈とマニュアル上の要件判定を区別する。
- 不鮮明、対象外、情報不足、読み取り不可の写真については**推測して合格扱いしない**。不足している写真・情報を尋ねる。
- 写真の取り扱い・保存は、既存の組織の情報管理ルールに従う。
- 公式仕様では、Copilot Studioのファイル入力を有効にでき、Teamsも対応チャネル。既存トピックで添付ファイルを取得する必要がある場合、`System.Activity.Attachments` と `First(System.Activity.Attachments)` を確認する（複数枚なら1枚だけで打ち切らず全件対応を検討）。

## 4. 機能要件B：修理方法を質問された場合

### 4.1 振り分け

- 「この部位の修理方法は？」「〇〇の補修手順を知りたい」など、**修理方法・工法・手順の照会**は、既存のマニュアル確認／検索経路へ送る。
- **現場状況の更新・写真の追加**は通常の現場アドバイス経路に送る。
- 修理手順に関する質問と現場報告の両方が明確な場合は、意図を取り違えず必要に応じて両方に対応する。緊急度が高い現場の安全情報を埋もれさせない。
- 修理方法の回答後も、**モード固定・会話終了・強制リセットをしない**。次の現場報告で通常ルートに復帰できるようにする。
- 既存の「マニュアル改訂」分岐も保持し、修理質問をすべて改訂ルートへ誤振り分けしない。

### 4.2 Teamsへの回答

**このルートだけは4項目の固定フォーマットを要求しない。** 正確さ・分かりやすさ・速さを優先する。

推奨例（質問に合うよう柔軟に短縮する）：

```text
🔧 修理方法のご案内

■ 結論
確認できたマニュアルの範囲で、該当する手順の要点を説明します。

■ 必要な条件・確認事項
・適用条件、事前に確認すべき事項

■ 手順の要点
・マニュアルに記載された順序に沿って簡潔に説明

■ 根拠
・文書名／文書番号／章・節（確認できたもののみ）

■ 補足
・資料に記載がない点、不明点、社内確認が必要な点
```

- **社内マニュアルの該当部分を検索してから回答**する。社内規定にない具体的な修理指示を一般知識から補わない。
- 適用条件・禁止事項・資格・承認・安全上の前提を省略しない。
- マニュアルに記載がない、検索不能、記述が矛盾する場合はその事実を明示し、必要な確認先へ案内。**根拠を捏造しない**。
- 同じ質問への重複したナレッジ検索や無関係なトピック起動を減らし、速度を改善する。
- Teamsに返した**同じ回答文章**をSharePointにも保存する（記録種別を区別）。

### 4.3 修理方法の保存とPower Apps互換

- 修理回答は、Teamsへ表示した**最終版の可読文章と同一のテキスト**をSharePointに保存する。
- 既存Power Appsが現場アドバイス専用の固定パーサーを使う場合、修理回答をそのまま同じ解析対象に流して表示を壊してはいけない。
- 既存列構成を調査し、**既存フォーマットは維持**した上で、必要に応じて互換性を損なわない`RecordType`相当の列、修理回答用テキスト列、または既存運用に沿った種別管理を行う。
- 新しい列の追加が必要なら、理由・型・Power Apps側の最小変更点を明記し、既存アプリの表示／更新を後方互換に保つ。

## 5. 機能要件C：SharePointへの確実な登録と既存Power Appsの維持

### 5.1 保存内容（重要）

**現場アドバイスの場合は、必ず二つの用途を分ける。**

| 出力先 | 保存・表示内容 | 目的 |
|---|---|---|
| Teams | 3章の①〜④の人間向け回答 | 現場担当者がその場で理解する |
| SharePoint | **現在のPower Appsが読める、従来どおりの書式・列構成の文章** | 事務所の既存画面を壊さず継続利用 |
| SharePoint（可能なら追加列） | 案件ID、回答種別、判定日時、優先度・状態、前回比較用データ、根拠等 | 堅牢な比較・将来の保守 |

**修理方法の場合:** Teamsに表示した可読回答文を**同文でSharePointへ保存**する。保存する種別・列は既存アプリが誤解析しないように設計する。

### 5.2 既存出力互換のルール

- 最初に既存Power Appsの式・画面・SharePoint列名を調査し、**どの文章のどの見出し・区切り文字・改行・記号・項目を解析しているか特定**する。
- 既存アプリ用文章の項目・順序・キーワード・区切り文字を**断りなく変えない**。既存の解析が動くことを回帰テストで証明する。
- 既存Power Appsのリフレッシュ／新着検知の仕組みを維持する。アプリを全面的に作り直さない。
- AIにTeams用文章からアプリ用文字列を**再解釈させる**のではなく、可能なら**一度確定した判断データ**から表示文と保存文を別々に構築する（下記6章）。
- 既存の文字列パーサーを最優先で維持。新しいデータ列やJSONは**内部補助**とし、既存列をいきなりJSONへ置き換えない。

### 5.3 TeamsだけSharePointが更新されない問題を必ず解決

下記の順序で**原因を特定してから**改修する。

1. **Microsoft 365 Copilotで正常登録される経路をトレース**し、SharePointで「項目の作成／更新」を行う真の実行元（トピック、エージェントフロー、Power Automate、別の連携など）を見つける。
2. 同一内容をTeamsで送り、**実際にどのトピック・フロー・ツールが起動したか**比較する。
3. **フロー実行履歴なし:** 起動条件、ルーティング、トピック分岐、公開・バージョン差、Teams添付の受渡しを確認する。
4. **実行履歴あり・失敗:** 接続参照、実行ユーザー／認証、権限、入力、環境差、SharePointサイト・リスト選択を確認する。
5. **フロー成功・未登録:** 分岐条件、書込み先の不一致、書込み対象ID、成功と誤認しているアクション、後続処理を確認する。
6. 既存PAの**「項目が作成されたとき」**トリガーを、**項目を書き込む処理だと誤認しない**。それは下流の反応側。必要なら書込み元を明示的なフロー呼出しに統一する。
7. Teams投稿から**確実にSharePointへ反映**されるよう、必要な場所で登録処理を呼ぶ。生成AIの任意判断だけに必須保存処理を任せず、明示的な呼出し経路・検証・エラー処理を設ける。
8. 同じ投稿のリトライで**重複レコードを大量作成しない**。元メッセージ／案件ID等を使った重複防止を検討する。
9. 失敗時にTeamsで「保存しました」と虚偽の表示をしない。**回答の表示**と**記録の成功**を識別し、保存失敗時の再試行／通知方法を設計する。
10. 既存Microsoft 365 Copilot経路での正しい動作も維持する。

### 5.4 Power Automate（必要なら）

SharePoint書込みの実行経路が曖昧である場合、**既存エージェントのトピックから明示的に呼ぶ保存用エージェントフロー**を候補とする。既存方式が健全なら無理に全部再構築しない。

- トピックから呼ぶフローの仕様は、環境に応じて `When an agent calls the flow` と `Respond to the agent` を確認する。
- 既存SharePointリストのサイト・列マッピング・接続参照を使う。
- **保存対象が現場アドバイスか修理回答か**を区別する。
- 既存フローの通知やPower Apps連携が依存するトリガーは残す。
- 同期処理のタイムアウト制約、保存の失敗／再試行／二重登録を考慮する。

## 6. データ設計・ルーティング（推奨実装）

### 6.1 1回の判断から二つの回答形式を作る

可能な限り、判定済み内容を内部的に次のような**正規化データ**として管理する。以下は**設計イメージであり、既存SharePoint列の定義ではない**。

```json
{
  "schemaVersion": "1",
  "caseId": "A-001",
  "recordType": "field_advice",
  "sourceChannel": "msteams",
  "reportSequence": 2,
  "observations": ["確認できた現場情報のみ"],
  "actions": [
    {
      "itemId": "EXISTING_ITEM_KEY",
      "label": "項目A",
      "priority": "high",
      "state": "needs_confirmation",
      "reason": "根拠または不足している情報",
      "sourceRef": "確認できた原文の出典"
    }
  ],
  "priorityChanges": [],
  "questions": ["追加で確認したい内容"],
  "nextActions": ["確認済み根拠に基づく次の行動"],
  "teamsText": "Teamsに表示する可読文章",
  "appsLegacyText": "既存のPower Appsが読む従来の文章"
}
```

- `recordType`: 少なくとも `field_advice` / `repair_guidance` を区別する（実際の実装名は既存と整合）。
- `itemId`: 文言が少し変わっても比較できるよう、既存初動措置項目の**安定した識別子**を利用。なければ対応表を作る。
- `caseId`: 既存の案件識別方法と整合。レコード新規作成ごとのIDと、同じ現場案件を継続して参照するIDを混同しない。
- `teamsText` と `appsLegacyText` は**同じ判断から生成**し、相互の内容を矛盾させない。
- 写真からの観測事実、マニュアルによる要件判定、ユーザー自己申告を混ぜずに保持する。

### 6.2 ルーティングと状態遷移

```text
入力（Teams：文章／画像）
    ├─ 現場報告／新たな現場情報／追加写真 → FIELD_ADVICE
    ├─ 修理方法・工法・手順の質問       → REPAIR_GUIDANCE
    ├─ マニュアル改訂の依頼            → EXISTING_REVISION_ROUTE
    └─ その他                         → 既存ルーティング／確認質問

FIELD_ADVICE → Teams用4セクション + SharePointの既存Apps用文章
REPAIR_GUIDANCE → Teams用わかりやすい自由形式 + SharePointへ同文保存

REPAIR_GUIDANCEを経由した後も、次の現場報告はFIELD_ADVICEへ遷移できる。
```

- **修理回答を行ったという理由で案件の前回優先度を上書きしない**。次の現場報告は前回の `field_advice` を参照する。
- 以前の画像・会話に依存する場合は、保存された案件事実を参照し、チャットの曖昧な長期記憶だけに頼らない。
- 不明な情報があるときの再質問は短く。何度も同じ質問を繰り返さない。

## 7. 回答速度・信頼性・正確性

**速度改善は今回の必須要件。** ただし、速度のために根拠照合・保安上必要な確認・保存処理を省略しない。

1. 正常な修理質問では**関連マニュアルを最短経路で検索**し、不要な画像解析・別種別のナレッジ検索・同じ検索の繰り返しを避ける。
2. 既存ナレッジの参照先を棚卸しし、**古い／重複／無関係なソースへの検索**を削減。最新の正規マニュアルに限定すべき場面を明確化。
3. エージェントの**トピック名・説明・起動条件**を見直し、誤ルーティングや不要なトピック連鎖を減らす。
4. 現場アドバイスは、現場の変更差分を重視し、毎回すべてを無条件に長文再生成しない。ただし、必要な安全確認と判断結果は省略しない。
5. SharePointへの検索は同一案件の必要な最新レコードのみ取得し、列の絞り込みやフィルターを検討する。
6. 不要なフローの連鎖・SharePointのポーリング待ちを削減。**新規登録を待つ「項目が作成されたとき」フローの検知遅延**と、エージェント自身の応答遅延を区別する。
7. Teamsの返信は可能な限り**1回の明快な最終回答**にする。処理に時間がかかる場合の受付中表示は許容するが、回答や保存を完了したと偽らない。
8. **修理回答の速度を重点測定**する。変更前後の実測値を同条件で比較し、数値で報告する。
9. エラーやタイムアウトがあれば、エラー内容をログに残し、ユーザーには簡潔な再試行案内を返す。処理を無限に回さない。

**計測:** Teams実機（スマホ）で各種テストを複数回行い、`投稿→最終回答表示`、`投稿→SharePoint反映`、必要に応じて `投稿→Power Apps確認` を分けて測る。改善前の値が取れるなら比較し、取れない場合は改修後の実測を記録する。**未計測で「高速化できた」と報告しない。**

## 8. 絶対に壊してはいけないもの（後方互換）

- 既存Copilot Studioエージェント本体の識別、公開可能性、Teams／Microsoft 365 Copilotでの既存正常動作。
- 以前からある**マニュアル確認・マニュアル改訂・現場アドバイス**の分岐、各トピック、専門ナレッジ検索。
- 保安柵、ポケット警報器、濃度等の初動措置ロジック。特定のMS番号を他番号へ勝手に読み替えない。
- 写真2回目以降の引継ぎ、追加報告、割込み、過去判断との比較（既存実装がある部分）。
- SharePoint側の既存サイト、リスト、重要列、CaseIdの運用、重複防止、既存Power Automate依存処理。
- **既存Power Appsが解析する文字列形式**および画面表示。使われている区切り記号・見出しを変えない。
- 既存の社内マニュアル参照先、認証・アクセス制御・監査要件。

**「Teams用の見た目をよくするため」にSharePoint用文字列まで変更しない。**

## 9. 実装順序（この順番で進める）

### Phase 0｜現状分析とベースラインの固定

- リポジトリのファイル構造とエクスポート、トピック、ナレッジ、フロー、Power Apps式、SharePointマッピングを調査。
- 現行の**3系統分岐と入力／出力／保存フロー**を図式化。
- Copilotでは保存成功・Teamsでは未保存となる差をトレース（可能なアクセス範囲内で）。
- 既存Power Appsが解析する文章のサンプルを取得し、**互換性テスト用のゴールデンデータ**として保持。
- 現行ファイルと設定をバックアップし、変更対象を明示する。

### Phase 1｜Teamsで正常に現場アドバイス／画像入力／SharePoint記録できるようにする

- Teams添付画像の認識、正しいトピック選択、判定、保存を一連で動作確認。
- 必要ならCopilot StudioからSharePointへの保存処理を明示化。
- **Teamsの投稿がSharePointに必ず登録され、Power Appsに反映される**ことを優先して直す。

### Phase 2｜現場向けの回答形式・前回比較

- ①変更点（初回は非表示）、②高・中・低、③確認事項、④ネクストアクションをTeamsに表示。
- CaseId単位の直前現場報告との差分処理を実装。
- 同じ判定から既存Apps用文章を従来の構文で保存。

### Phase 3｜修理方法の高速検索と現場フローへの復帰

- 修理質問を正確に既存マニュアル検索へ振り分け。
- Teamsに短く・根拠付きで回答。
- **Teamsと同じ修理回答テキスト**をSharePointに保存。
- 修理回答のあと現場情報更新で現場アドバイスへ戻ることを確認。

### Phase 4｜スマホ実機テスト・回帰テスト・改善

- Teamsのスマホ実機、Microsoft 365 Copilot、SharePoint、既存Power Appsを含むEnd-to-End検証。
- 不具合を修正し、速度計測・根拠照合・セキュリティ確認。
- 手順書と変更点・未解決点を残す。

## 11. 成果物の要求

Codexは、単なる提案で終わらず、次を提供すること。

1. **調査結果**：現在の処理経路、TeamsだけSharePointが更新されない原因（確定／推定を区別）、既存アプリが読んでいる形式。
2. **実際の変更ファイル**：トピックYAML／設定／Power Automateフロー定義／テスト等、提供されたファイル内で編集できるもの。
3. **適用手順**：Copilot Studio、Power Automate、SharePoint、Teamsの管理画面で変更が必要な場合、実際の画面項目と設定内容を順序立てて明記。
4. **後方互換の証拠**：既存Power Appsの文章形式の変更前後比較、マニュアル確認・改訂分岐の回帰結果。
5. **テスト結果**：上記T01〜T19の合否、実行できなかった項目、確認できたログ／スクリーンショット／保存レコード例。
6. **性能結果**：修理質問などの実測応答時間。旧値と比較できる場合は差も示す。
7. **未対応事項**：権限不足・接続不足・環境制約などにより未実装の作業を一覧にし、次の実施手順を記載。

**最終報告の必須フォーマット:**

```text
【実装完了】
・具体的に変更した内容（ファイル名・処理名つき）

【検証済み】
・何を、どこで、どの条件で確認したか

【未検証／環境側作業】
・何が足りず、どの設定・接続が必要か

【既存機能への影響】
・互換性確認の結果、残存リスク

【応答速度】
・実測値、比較、改善点
```

**重要:** コードや構成を変更しただけで、実環境のTeams投稿・SharePoint反映・Power Apps表示まで確認していない場合は、**「コード修正完了／本番動作未検証」**と正確に報告する。「すべて完成」「問題なし」と断定しない。

## 13. 最後の確認事項（Codexへの指示）

今回の完成形は、**「現場＝Teamsだけで写真を送り、読みやすいAI回答を受ける」「事務所＝従来どおりPower AppsでSharePointの判定を閲覧する」**という二つの利用体験を両立すること。

- **Power Appsから現場が質問を送る画面は、今回は作らない。**
- **新しいエージェントを増やして既存構成を分割しない。**
- Teams側回答の改善だけでなく**SharePoint登録まで**が改修範囲。
- **修理方法の回答は自由形式、正確・分かりやすく・高速、SharePointには同文保存**。
- **現場アドバイスの①変更点は2回目以降のみ**、②高・中・低、③確認、④ネクストアクションの順。
- 修理質問のあとに現場情報が届けば現場アドバイスへ**確実に復帰**。
- **動作中のマニュアル確認／改訂、既存Power Apps用書式、他機能を犠牲にしない。**

以上を満たす差分改修を、検証可能な形で進めること。
