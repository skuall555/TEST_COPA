# 導入手順

この配布ZIPを「ソリューションのインポート」へ直接渡すことはできません。既存エージェントのトピック編集と、実環境から取得した保存フロー・列の確認に使います。まず同じ環境構成のテスト環境で行ってください。

## 1. バックアップと実値の確認

1. Power Appsメーカー画面で対象の**環境**を選択。「ソリューション」から既存エージェント、関連クラウドフロー、接続参照を含む未管理ソリューションをエクスポートします。フローだけのZIPと本パックを混同しないでください。
2. Copilot Studioで現在のエージェント名・ID・公開日時、各トピックのコード、エージェントの「指示」、ナレッジ一覧、Teamsチャネル設定を控えます。
3. [保存経路の調査](保存経路の調査.md)で、M365 Copilotの正常な書込み実行元を確定します。候補の保存フローIDは `9a770168-65a8-f111-aaad-7ced8d2f9cab`。**このIDのフローが今も対象環境に存在するか確認**します。
4. SharePointで実リストを開き「設定→リストの設定」。列を開いたURLの `Field=` は内部列名の確認に使えます。表示名だけでマッピングしません。サイトURL、リストGUID、列の型・必須・索引・一意制約、プレーンテキストかを確認します。
5. 必要なら認証済みブラウザーから次の読み取り専用RESTを開き、JSONをローカルに保存します。サイト／リストGUIDは実際の値へ置き換えます。トークンをURLに含めません。

```text
実サイトURL/_api/web/lists(guid'実リストGUID')/fields?$select=InternalName,Title,TypeAsString,Required,ReadOnlyField,Indexed,EnforceUniqueValues,RichText,Choices
```

列型にないプロパティでエラーになる場合は基本プロパティだけで取得し、NoteのRichTextとChoiceのChoicesを個別に確認してJSONへ補います。ジェネレーターは実列定義を確認せず通すために値を補完しません。

6. 既存Appsを編集モードで開き、データソース、ギャラリーの `Items`、見出しを抽出する `Split/Mid/Find`、`Refresh`・タイマー等を控えます。現場回答の実保存サンプルを1件取得し、変更前のApps表示と対応させます。`.msapp` と式はこの作業時点で初めて確認できます。
7. `case_id` が案件を継続するIDか、新規作成行のIDか、同一案件を追記するか更新するかを実履歴で確認します。既存重複防止・下流通知の条件も確認します。

## 2. 保存経路を選ぶ

**A：既存保存経路を修正する。** 正常なM365経路と同じ既存フローをTeamsから確実に呼び、接続・認証・公開差を直せる場合はこちらを優先します。`topics/` は旧保存フローの入力を維持しています。ただし修理回答は `text_1="マニュアル確認"`、`text_3="修理回答"` として渡すため、実フローで修理種別を識別し、Appsの現場用解析列へ混入させない設定が必要です。旧フローの実際の契約と異なる場合はここを実定義に合わせます。互換版のローカル比較は同一返却IDが確認できる範囲です。

**B：実値に結び付けた保存アダプターを使う。** 既存リストが履歴追記型で、その方式が既存Apps・通知と両立することを確認できた場合に使えます。新しいエージェントは作りません。保存用フローのみを同じ既存エージェントの明示呼出しに結び付けます。既存がCaseId一意の更新型なら、この生成物は適用せず既存更新方式を残して個別調整します。

### B-1. 列とAppsの確認

`contracts/deployment.example.json` を **`deployment.local.json`** へコピーし、次を実値で設定します。nullやテスト用の値では生成できません。

| キー | 入力する実値／確認方法 |
|---|---|
| `site_url` / `list_id` | 実際の保存先サイトURL・リストGUID |
| `flow_id` | 次項で作成／利用するエージェントフローの実GUID |
| `connection_reference_logical_name` | ソリューションのSharePoint接続参照の論理名。表示名や接続IDではない |
| `field_map` | 実際の内部列名。詳細は保存フロー契約を参照 |
| `record_type_values` | 実際に使う現場／修理の識別値。Choiceなら選択肢に存在させる |
| `static_fields` | タイトル等の追加必須列に設定する既存ルールに沿った値 |
| `storage_mode` | 追記方式を確認した場合だけ `append_history_verified` |
| `identity_binding_verified` | 認証ユーザーと所有者キーの対応、フロー呼出し権限を確認して初めてtrue |
| `powerapps_repair_filter_verified` | 次のApps調整を実機で確認して初めてtrue |

列は実在するものを再利用し、足りない補助列だけを管理者の既存運用に沿って追加します。**既存のApps解析列を別用途へ変更しません。** 修理用列と従来の現場回答列を分離します。補助列の一意・索引条件は [保存フロー契約](保存フロー契約.md) を参照。

既存Appsのデータソースを更新して列を認識させ、現在の `Items` 条件を維持したまま「修理種別を除外」する条件を追加します。例は概念だけです。次をそのまま貼らず、実名・列型に合わせます。

```powerfx
// Text列の概念。既存の検索・権限・案件条件も維持すること。
Filter(既存データソース, 既存条件, IsBlank(実種別列) || 実種別列 <> 実修理種別文字列)
// Choice列の場合は 実種別列.Value で比較する。
```

旧行の種別が空白でも表示を残します。非委任警告、表示上限、新着検知、Refresh、通知フローの対象種別を確認します。修理レコードの空の現場解析列をパーサーへ渡さず、事務所で修理を見せる場合は修理用列を表示します。Apps本体を全面改修する必要はありません。

### B-2. エージェントフローを用意・生成する

1. 対象ソリューション内で「エージェントがフローを呼び出したとき／When an agent calls the flow」と「エージェントに応答する／Respond to the agent」を使うフローを作成するか、同種の既存フローをテスト環境で使用します。公開HTTP受信や認証無効化は使いません。
2. SharePoint接続は承認済みのアカウントを使います。サイト閲覧・追加権限と、実行者／接続所有者／DLPポリシーを確認します。接続参照をソリューションに含めます。
3. 保存し、ソリューションを未管理でエクスポート。実フローGUID・接続参照の論理名を確認し、設定へ入れます。Power Platform CLIの `pac solution unpack` でローカル展開します。
4. `fields.local.json` は前項で取得した実列定義です。`value` 配下の配列、または配列そのものを受け付けます。次のコマンドは**このパックのルート**で実行します。

```bash
python tools/flow_definition.py --config deployment.local.json --fields fields.local.json --output deployment-output/agent-flow.json
python tools/bind_adapter.py --config deployment.local.json --fields fields.local.json --output-dir deployment-output/topics
```

先に `deployment-output` ディレクトリを作成してください。列未確認・Apps除外未確認・CaseId一意の更新方式では生成を止めます。テストfixtureで検証を通す運用はしません。

5. エクスポートしたフローのJSONへ定義だけを当てたコピーを作ります。`--workflow` は**実際の展開先にある、対象フローGUIDを含むJSON**です。メタデータや既存エージェント識別は保持します。

```bash
python tools/patch_export.py --unpacked-dir /actual/unpacked-solution --workflow /actual/unpacked-solution/Workflows/Actual-GUID.json --generated deployment-output/agent-flow.json --config deployment.local.json --output-dir /actual/patched-solution
```

6. `pac solution pack` でコピーをパックし、**テスト環境**へインポート。SharePoint接続参照を実接続へ割り当て、フローデザイナーでトリガー・全アクション・レスポンスが有効か確認します。ConnectorのPostItem動的列やテナントの出力制約は実環境での確認が必要です。この生成JSON自体はインポート可能なSolution ZIPではありません。
7. フローをオンにし、Copilot Studioのトピックから選択できることを確認します。9入力・8出力の文字列契約をデザイナーと照合。入力名が環境で再採番された場合は `deployment-output/topics` のbindingを実メタデータへ合わせます。通常モードと画像単発モードを確認します。

既存の索引フロー・マニュアル確認／改訂保存フローは削除しません。アダプターを現場と修理に使う場合、同一案件の現場書込みが別保存経路へ分散しないよう確認します。

## 3. 既存3トピックと指示を適用

1. 同じ既存エージェントの「トピック」を開き、バックアップ後、コードエディターへ全文を貼り付けます。画像→3-9の論理名 `cr88f_SUBARU_search.topic.9xY` は既存参照です。対象環境の論理名が違う場合はエクスポートと照合して参照だけを直します。
2. Aなら `topics/`、Bなら `deployment-output/topics/` の3ファイルを使います。両版を混在させません。新しいエージェントを追加する操作ではありません。
3. エージェント「概要→指示」へ `topics/エージェント指示_Teams追記.txt` の全文を反映。既存テナント独自の追記がある場合は消さずマージします。
4. トピックチェッカーでエラーがないことを確認。追加String入力 `判定応答方式` は通常の呼出しでは省略、画像トピックからだけ「画像単発」です。既存AI Builderモデル・索引フロー・保存フローが解決するか確認します。
5. 実行中トピックの質問への返信を優先する設定を維持。親エージェントがナレッジから自由回答してトピックを飛ばさないか、テストの追跡で入口→3-9→保存→質問待ちを確認します。指示文だけではオーケストレーション設定は変わりません。

## 4. スマホTeamsと写真

1. 同じエージェントの「設定」でファイル／画像入力に関する項目がある場合は有効化し、テナント・チャネルでの対応可否を確認します。設定名はリリースで異なります。公式の画像入力／ファイル受渡し資料を参照してください。
2. 「チャネル→TeamsおよびMicrosoft 365 Copilot」から同じエージェントを公開・更新。スマホの**個人チャット**でテストします。古いアプリ版・別環境・別エージェントの会話と混同しません。M365正常経路も同じ版で回帰します。
3. JPEG/PNGを「写真です」と添付し、追跡で4-9が実行されたか、`System.Activity.Attachments` の件数・Name・ContentType、既存モデルのImageInputへ渡った値の型を確認します。機密写真や添付参照URLを公開ログへ貼りません。
4. **`application/vnd.microsoft.teams.file.download.info` 等のメタデータしかない場合、このパックはそれを画像としてAIに渡しません。** 権限を持つOneDrive/SharePoint等の標準コネクターで、その添付に対応するファイル内容を取得→既存画像プロンプトのImageInputへファイル内容を渡すチャネル用アクションの接続が別途必要です。実際の添付構造・格納先・実行者権限が未提供なので、その取得フローは未実装です。URLを一般のHTTPツールへ無条件に渡したり、認証を解除しません。
5. 実データの受渡し後、既存プロンプトの `ContextText` と `ImageInput` を使い、ポケット警報器・可燃性ガス検知器・表示シートを別々に検証。写真を読めなかった場合は実施済みにしません。1枚目、追加2回目、修理後の画像、複数添付を試します。
6. HEIC等で送られる場合は実際にPNG/JPEGへ変換できる承認済み経路を確認するか、送信者がJPEG/PNGとして添付します。拡張子の変更だけでは変換できません。

## 5. 失敗時・タイムアウトと公開

接続版フローはSharePoint失敗を `status=failed` として返し、回答に保存未完了を表示します。応答前にトランスポート自体が失敗した場合は通常の後続ノードが動かないため、**テナントの既存「エラー発生時／OnError」システムトピック**で次を設定します。現行OnErrorのソースがないため本パックでは上書きしていません。

1. エラー時に `Global.TeamsPendingReply` が空でなく、`TeamsPendingOwner=System.User.Id`、`TeamsPendingActivityId=System.Activity.Id` の場合だけ、その回答＋「記録の完了を確認できません。再送前に記録状態を確認してください」を送る。
2. 送信後 `TeamsPendingReply` を空にする。その他のエラーは既存処理を維持。内部エラー・秘密情報を利用者へ出さない。
3. フロー内の標準コネクター再試行は1回。会話の自動再送ループを追加しない。タイムアウト後は実行履歴とEventKeyを確認してから手動再送する。

最終回答表示後のフロー失敗、フロー成功後の返信失敗、重複再送の3パターンを試します。二重返信まで含む厳密な一回配信は未検証です。既存AppsのRefresh・通知検知を含むT01〜T19を実施し、必須項目が揃ってから本番公開します。
