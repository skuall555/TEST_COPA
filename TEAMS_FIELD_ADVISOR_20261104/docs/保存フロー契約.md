# 保存アダプターの契約

`tools/flow_definition.py` は、確認済み設定と実列定義からPower Automateのworkflow JSONを生成します。出力はソリューション全体ではありません。実フローのエクスポートへ定義を適用する際も、実GUID・接続参照・メタデータを保持します。

## 入出力

トリガーと応答は `Request / Skills`、`Response / Skills`。入力9個、出力8個、すべてStringです。実デザイナーのメタデータと照合してください。

| 入力 | 値 |
|---|---|
| operation | save / load。活動ID等が不足したsaveはinvalidを渡し、保存を拒否 |
| case_id | 継続する実案件ID。SharePointの作成行IDではない |
| owner_key | 認証された利用者に対応する安定ID |
| event_key | チャネル＋会話ID＋利用者ID＋活動ID＋回答種別。同じ活動の再試行を識別 |
| record_type | 契約上field_advice / repair_guidance。実リスト値へ設定でマッピング |
| legacy_text | 現場は既存7見出しの全文、修理は最終表示文の全文 |
| current_snapshot | 現場の `P01\|高\|要確認` のような3列行を改行で連結。修理は空 |
| facts_history | 初報＋追加履歴。モデルの曖昧な長期記憶の代わりに保存する事実履歴 |
| source_channel | msteams等の元チャネル。現在の生成版ではEventKeyのチャネル区別に使い、別列は作らない |

| 出力 | 意味 |
|---|---|
| status | saved / duplicate / loaded / failed |
| case_id / item_id | 実案件ID / 保存行ID。混同しない |
| teams_text | 保存時に確定した表示文章。重複時も初回保存文を返す |
| previous_status | found / none / unavailable |
| previous_snapshot | 修理を除外した前回現場判定 |
| case_facts | load時に取得した直近現場事実 |
| error_code | 診断用固定コード。秘密情報を含めない |

返却成功はPostItemが成功した後です。処理内のGetItems/PostItem失敗・タイムアウトはfailed。フロー呼出し自体の障害はシステムOnErrorで別途扱います。保存前に表示用fallbackを `Global.TeamsPendingReply` に保持しますが、既存OnErrorへの設定は環境作業です。

## 実列のマッピング条件

| field_mapの役割 | 必要な実列型・条件 |
|---|---|
| case_id | Text、索引あり。一意制約なし（この版は追記型のみ） |
| event_key | Text、索引＋一意制約。重複挿入を防止 |
| owner_key | Text、索引あり |
| record_type | TextまたはChoice、索引あり。Choiceなら実際の選択肢を確認 |
| legacy_text | 既存Apps用のプレーンな複数行テキスト。内容の区切りを変えない |
| repair_text | 修理専用のプレーンな複数行テキスト。legacy_textとは別列 |
| current_snapshot | 比較用プレーンな複数行テキスト |
| facts_history | 案件事実用プレーンな複数行テキスト |
| teams_text | 確定したTeams表示用プレーンな複数行テキスト |

すべて実在する内部列名で指定します。リッチテキスト、同じ列の二重利用、未マップ必須列、未知の列は生成を拒否します。列の最大長やリストしきい値も実運用で確認してください。EventKeyはSharePoint Text列の文字数上限以内であることが必要です。長いTeams会話IDで超過する場合は、実環境で承認したハッシュ等に置き換えてから同じ活動の再試行を検証します。本版はハッシュ化を実装していません。

## フローの順序

1. 必須入力と操作を検証。
2. saveはEventKey＋所有者で重複を検索。存在する場合は作成せず保存済み本文を返す。
3. 現場は正規化データと7見出しを検証。CaseId＋所有者＋現場種別、ID降順、Top 1で前回を読む。修理はこの検索を行わない。
4. 優先度／状態／新規／今回未判定をData Operationsで比較。生成AIや項目ごとのSharePoint呼出しは使わない。旧レコードに比較データがない場合は比較不可を明示。
5. 同じ判定からTeams表示を生成。Apps用文章は入力のまま保存。修理はTeamsと同じ本文を修理用列へ保存。
6. 作成成功後に返却。重複・失敗は別status。

フローの同時実行数は1です。このフロー経由の比較→保存の順序を守りますが、別フローや手動の並行書込みをロックするものではありません。全ユーザーを直列化するため高負荷時の待ち時間は実測が必要です。大規模運用では既存方式を保った案件単位の整列や排他を別途検討します。

loadはCaseId＋所有者を確認し、最新の**現場**事実・判定を返します。修理だけの案件は現場履歴が空のままです。履歴がない事実を捏造しません。

## 権限と限界

所有者条件はデータ混在を防ぐ条件です。サービス接続が持つ権限を縮小するサーバー側認可ではありません。対象フローは既存認証済みエージェントからだけ呼べるよう、実行権限・接続・DLPを設定します。`System.User.Id` のチャネル差を確認し、M365とTeamsの横断再開が必要なら実際の認証IDへ統一します。確認してから `identity_binding_verified=true` にします。

既存が更新型・別の重複制約を持つ場合、この追記版を強行適用しません。下流の「作成されたとき」通知は現場／修理の追加双方で起動し得るので、実フローの種別条件を確認します。厳密な二重返信防止とトランスポート障害からの回復、複数ユーザー性能、実コネクター動的スキーマはテナント試験の対象です。
