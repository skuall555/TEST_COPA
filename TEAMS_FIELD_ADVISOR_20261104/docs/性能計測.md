# 応答速度

**Teams実測値はNOT_MEASUREDです。** 投稿→回答、SharePoint反映、既存Apps表示の時間を取得できていません。高速化したとは報告しません。

コードでは、表示の作り分け・前回差分をPower Fx／フローのデータ演算で行い、追加の生成AI呼出しを避けました。修理への早期分岐、既存根拠検索を保持し、通常の修理質問に画像解析を追加していません。保存アダプターは最新現場1件だけをフィルター検索し、措置ごとのSharePoint呼出しや「項目が作成されたとき」のポーリング待ちは行いません。

一方、同期保存、初回案件読込み、直列実行による待ち時間が増える可能性は残ります。画像は最大5件を順次解析するため、枚数に応じた時間が必要です。既存の画像ガイド検索やマニュアル根拠取得は削除していません。検索先の古い・重複文書の有無は実テナントのナレッジ一覧を取得して確認します。

## 実機計測の方法

1. 同じ端末・ネットワーク・ユーザー・案件入力で、変更前／後を各3回以上実行。初回とウォーム状態を分けます。
2. シナリオは文字初報、文字続報、写真1枚、写真2枚、修理質問、修理後の現場写真。`validation/performance.csv` へUTC時刻を記録します。
3. 投稿時刻、最終返信表示、実SharePoint作成／更新、Appsで確認できた時刻を別々に取得。受付表示だけを最終回答と数えません。
4. Copilot追跡・フロー履歴で、目的分類、ナレッジ、画像モデル、優先度生成、前回検索、保存、Teams返信の所要時間を記録します。生写真・トークンはログへ転記しません。
5. median、最小／最大、失敗／再試行を報告します。変更前が取れなければ改修後だけの実測と明記。下流通知の検知遅延をエージェントの返信遅延から分けます。

## 残る改善判断

修理検索が支配的なら、実際に参照された正規マニュアル・索引・重複検索を確認して対象を絞ります。保存待ちが支配的なら実接続・索引・同時実行を調べます。比較元取得が支配的なら実リストの索引とデータ量を確認します。根拠照合や保存を省略して見かけの時間だけを短縮しません。
