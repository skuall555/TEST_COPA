# 追加報告の停止対策

今回の `不合格:itemEmergencyValid` は、EMERGENCYが `通常|理由` ではなく `通常 理由` になったためです。提示された原文を旧版のPower Fxに通して不合格を再現し、今回の式では区切りだけを補って受理できることを確認しました。

**2時間の待ち時間そのものは実機で再現していません。** 形式エラーの原因と、長時間待つ原因を同一だと断定していません。

## 適用方法

1. 待ち続けているテスト会話はリセットして終了します。保存し直しても、その実行が新版へ切り替わるわけではありません。
2. 現在の3-9のコードを控えます。
3. [3-9の最新版全文](3-9-緊急保安業務エージェント_optimized.yaml)をRawで開き、コードエディターへ**全文置換**して保存します。入口・画像分析・全体「指示」は変更しません。
4. トピックチェッカーを確認します。
5. 新しい会話で「台所でガス臭い」、続いて「メーターガス栓閉止。共用部で臭気有り。アパートの2階」を入力します。

**前回修正した自動再生成の条件ノードは、今回削除しています。古い条件やGotoを一部だけ残さず、今回の全文を使ってください。** 通常の追加報告を待つ質問は残しています。

## 変更点

- `通常 理由`、`高 理由`のように判定語と空白の境界が明確な場合は、語・理由を変えず区切りだけ正規化します。半角・全角空白、改行、タブを対象にします。
- `高ではない`、`不明 理由`、理由なし、複数区切り等は推測せず不合格とします。緊急度を補ったり、欠けた必須措置を生成したりはしません。
- EMERGENCYが不正なら残る組立を進めず、失敗側へ進みます。
- **形式不正によるAI自動再生成を廃止しました。** 利用者の追加入力なしに同じ優先度AIへ戻る経路はありません。
- 同じ診断Stringをv2へ更新し、モデル・結果検証・案件保存の区間が見えるようにしました。新しい変数はありません。

メーター閉止の対応済み、7見出し、高優先度の完了判定、要請・避難の高連動、既存の追加確認10回上限、修理・調査・画像割り込み、接続・保存フローは維持しています。

## まだ待つ場合に見る変数

`Topic.優先度経路診断` に **subaru-text-20261102-v2** が含まれていることを確認します。

| stage | 到達した区間 |
|---|---|
| beforeAI | 優先度AIを呼び出す直前。ここに留まれば、その呼出し以降の完了を待っている |
| afterAI | AIの出力を受領済み。まだ結果検証が完了していない場合を含む |
| gate | 形式検証後、成功条件を評価する直前 |
| beforeCaseSave | 合格後、案件保存フローの呼出し直前 |
| afterCaseSave | 案件保存フローの完了後 |
| wait | 利用者への追加質問待ち |
| failed | 形式不正等で失敗側へ進んだ |

この値は最後に通った地点です。区間内のどの処理で停止したかは、同じ実行の活動と時刻で確認します。モデルや外部フロー自体が返らない場合のタイムアウトを設定したわけではなく、壁時計時間の上限は保証できません。未確認のタイムアウト属性はYAMLへ足していません。

## 確認できたこと

回帰61件、Microsoft.PowerFx.Interpreter 1.8.1の197式、番号45入力、内部形式と成功条件46ケース、画像11特徴の受渡しに合格しました。今回の原文は旧版で拒否・今回版で受理され、メーター閉止済みは保持されています。明確な「高」の区切り欠落は高の連動を保ち、否定・未知の判定・理由欠落は拒否します。

制御フロー上、追加の利用者入力なしに優先度AIへ戻る経路がないことも確認しました。実モデル・Studioの読込・2時間の待ち時間・検索表示の発生元・外部処理の速度は未確認です。形式が合格でも、AIが付けた優先度や推定の正しさまで保証する検査ではありません。
