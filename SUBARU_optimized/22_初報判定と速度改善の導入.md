# 初報の要請・避難と速度改善の導入

**今回も3-9のYAML全文だけを更新します。** 入口・画像分析・全体「指示」・外側の画像プロンプトは変更していません。

## 変わる判定

「浴室で臭気あり」だけの通常の単独臭気の初報なら、消防・警察要請と避難誘導は **低** にします。実施状況が不明なら **低・要確認** です。情報が少ないことを理由に優先度を中へ上げません。

具体的な警戒兆候が報告された場合は中、E-01／E-02、強臭気・広域拡散・事故・制御不能等の危険条件が成立すれば高とします。既に高だった現場は、短い続報に危険の記載がないだけで低には戻しません。低は安全確認済みという意味ではなく、必要な確認と変化の監視は続けます。

P08上流遮断の建物・設備不明時の中、以前指定された基本措置の高、実施報告不明なら要確認という区別は維持しています。

## 導入

1. 現在の3-9のコードを控えます。
2. [3-9の最新YAML](3-9-緊急保安業務エージェント_optimized.yaml) をRawで開き、全文をコピーします。
3. Studioの既存の「3-9-緊急保安業務エージェント」のコードエディターで全文置換し、保存します。今回は表示処理も変えているため、プロンプトだけの部分貼付はしないでください。
4. トピックチェッカーを確認し、**新しい会話**で次の初報・続報の両方を試します。
5. 確認後、通常の公開手順で公開します。この環境からStudioへの保存・公開は行っていません。

最初に「浴室で臭気あり」で要請・避難が低になることを確認します。次に「別室は不在で入れず換気できない。ドアポストでLEL1％検知し、警報が鳴り止まない」と続報し、要請・避難が高へ上がることを確認してください。別の会話では複数地点反応・広域拡散・事故等の高を確認します。

## まだ遅い場合の確認

Studioのテストペインの活動で、次の区間を分けて実行時間を確認してください。

| 区間 | 確認すること |
|---|---|
| 入口の目的意味判定 | 最初の報告だけに時間がかかるか |
| answer_priority | AIの生成に時間がかかるか、同じターンに2回実行されていないか |
| 結果の検証・表示処理 | AI完了後から次の外部フローまでが長いか |
| invokeFlowAction_caseSaveFieldAdvice | 案件保存の外部フローが長いか |
| question_priorityUpdate | 結果が利用者へ表示される時点 |

初報と追加テキスト報告をそれぞれ数回試し、同じモデル・同程度の入力で比較します。初報には入口の意味判定が含まれるため、続報と分けてください。初回実行だけの遅さや混雑も分けて見ます。[計測用CSV](validation/speed_timing_plan.csv)の時間欄は空で、実測した結果のみ記入する形式です。

案件保存は従来どおり結果表示前に呼ばれます。保存フローが遅い場合は、この変更だけでは解消しません。保存を省略する、記録を失う、結果表示の順序を変える処理は追加していません。
