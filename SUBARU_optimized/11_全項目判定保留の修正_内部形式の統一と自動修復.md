# 全項目「判定保留」の修正

トピックチェッカーの型エラー報告への最新対応は [12](12_トピックチェッカー型エラー対策_型初期化と段階変数.md)。以下の旧診断変数は、最新版ではP5...へ変更している。

## 今回の報告と確認できた原因

利用者から、v3適用後に全優先度が「判定保留」となり、既報の対象・操作・濃度・警報を再入力するよう求める最終表示が報告された。

リポジトリ上の3-9で以下を確認した。

- `answer_priority.additionalInstructions` に「従来の8見出しだけ」と「内部3ブロックだけ」という二つの出力指示が共存していた。
- 呼出しプロンプトと参照する固定ガイドにも従来の出力書式が残っていた。
- 必須行、列数、引用、危険6行などの一つが不適合なら、全措置を保留の固定文で置き換えていた。内部で形式を修復する経路は無かった。
- 根拠引用にも `Trim` を適用していた。Power FxのTrimは連続する内部スペースも詰めるため、原文との文字列照合に影響し得た。

今回受け取ったのは最終表示であり、AIの生出力・実行履歴は取得していない。上記の不備はコードで確認したが、今回どの検査条件が落ちたかは未特定。旧形式を実際にAIが返したと断定しない。

## 修正内容

1. 固定ガイドから人向けの出力テンプレートを外し、判断ルールとしてのみ参照する。危険条件・閾値は維持する。メイン呼出しの本文とadditionalInstructionsは、内部3ブロックの一種類に統一する。完成した書式例を示す。
2. CRLF、全角区切り、フィールドの前後スペース、既知の措置名や「対応済み」の表記揺れを処理する。措置名の置換は先頭フィールド、実施状況の置換は状態フィールドに限定し、根拠の引用を名称正規化で書き換えない。
3. 根拠・フィールドにはTrimEndsを使用し、引用途中のスペースを保つ。根拠が報告中に存在すること、写真根拠には採用済み【写真有】があることの検査は維持する。
4. 不適合時だけ、元の現場入力・時系列履歴・前回出力を使って内部で1回修復する。修復結果は利用者へ直接送らず、同じ検査へ戻す。通常判定は従来どおり1回。修復回数は1判定につき最大1回で、同じ修復を繰り返さない。
5. 修復後にも不適合が残る場合、照合済みの措置を保持して表示する。不適合の措置・対象は未照合とし、実施済みや安全確認済みを捏造しない。同じ措置・同じ対象に矛盾する重複行があれば、その対象の行を採用しない。他の対象は残す。
6. 危険項目の根拠と一意性を各項目で照合する。継続警報と検知が個別に確認できれば、他の危険行が欠けても消防・警察要請の高を維持する。矛盾する危険行は肯定にしない。危険ブロック不適合時は要請を低と確定せず中で確認する。
7. 欠けた基本高項目は要確認として残す。実施を明示的に報告していないだけで未実施と断定しない。全体の整合が未完了なら、全て対応済みによる終了は許可しない。従来の全項目保留の固定表示と、同じ現場情報一式の再入力要求は除去する。

実施済みと効果未解決の両立、対象の区別、消防と警察の区別、MS-018廃止、案件保存、画像割り込み・復帰は維持する。AIの意味解釈や時系列判断そのものを、文字列の検査だけで保証するものではない。

## 導入手順：今回更新するのは3-9だけ

1. GitHubの最新版 `3-9-緊急保安業務エージェント_optimized.yaml` を開く。
2. Raw表示で全文をコピーする。
3. Copilot Studioの対応する3-9トピックのコードエディターで全文を置換し、保存する。
4. トピックのエラーを確認し、新しいテスト会話を開始する。旧会話の途中状態を継続して比較しない。
5. 既報の現場情報を順に入力し、当該室の閉止が実施済み／効果未解決、消防・警察の未要請が高になることを確認する。公開チャネルへの反映はテスト後に公開して確認する。

**今回、4-9画像分析YAML、AI Builderの画像カスタムプロンプト本文、エージェント全体の「指示」の変更は不要。** b81fbd1の4-9と全体指示はそのまま。画像モデルの選択と、今回の3-9内部出力修正は別の設定。

## 実行履歴で確認する値

| 変数 | 用途 |
|---|---|
| Topic.優先度書式版 | `priority-v4-20261023` なら今回版 |
| Topic.優先度初回構造化結果 | 修復前のAI生出力。後続の修復で上書きしない |
| Topic.優先度形式修復回数 | 通常0、内部修復を行った場合1 |
| Topic.優先度構造化結果 | 現在検査している出力。修復した場合は修復後 |
| Topic.優先度構造妥当 | ブロック・出現回数・順序の確認 |
| Topic.現危険妥当 | 危険6行全体の整合 |
| Topic.措置状態妥当 | 必須措置・状態・引用などの全体整合 |
| Topic.高優先度完了 | 全体整合と高措置の実施・必要な効果から計算 |

通常回答へ内部生出力は表示しない。いずれの変数も、この環境からCopilot Studio実機で読み取ったものではない。

## 検証結果と限界

オフライン検証75件（契約25、画像17、状態・形式修復33）。保存済みYAMLの式と分岐を限定的なPython評価器で実行し、内部AI修復の応答を模擬して検証する。旧8見出しからの修復、修復失敗時の最大1回制限、一項目不正時の閉止済み保持、別の危険行が欠けても要請高保持、重複矛盾の除外、空白・区切り・空応答・ブロック順序を含む。

実際のAIによる書式遵守・認識・意味判断、Copilot Studioの型検査・Power Fx実行、速度は未検証。前回の62件合格だけでは実機の今回の失敗を検出できなかったため、コードで確認した不備に対する再現条件を追加した。模擬応答の検証を実モデルの成功率として扱わない。

実機計画は `validation/priority_recovery_runtime_cases.csv`。全件NOT_RUN。内部修復が発生するとAI呼出しが1回増えるため、通常時と修復時の待ち時間を別々に計測する。画像認識の精度がこの修正だけで向上したとは主張しない。

差分は `diffs/priority_recovery_v4/`（b81fbd1基準）。従来の危険ルール、接続ID、フロー、入口トピック、画像トピック、原本資料は変更していない。ロールバックする場合は3-9だけb81fbd1へ戻せるが、その版には今回報告された全保留の問題が残る。
